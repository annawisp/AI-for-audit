# 收入循环智能审计助手测试任务书

## TTP-101：基础工程与运行底座测试

> 文档类型：**测试任务书（Test Task Plan）**  
> 本文档用于验证搭建任务 `TASK-101`，不属于智能体搭建任务书，不定义或新增产品功能。

| 文档属性 | 内容 |
|---|---|
| 测试任务书编号 | TTP-101 |
| 文档版本 | V1.0 |
| 对应搭建任务 | Stage 1 / Step 1.1 / TASK-101 建立项目代码结构 |
| 被测版本 | AI for Audit Backend / Frontend V0.1.0 |
| 测试类型 | 工程结构、安装启动、Smoke、异常、安全、CI、产品验收 |
| 不包含 | 数据库、文件上传、Evidence Object、审计程序状态机、合同解析、审计判断 |
| 测试结论 | 执行完成后填写：PASS / PASS WITH CONDITIONS / FAIL |

---

## 一、与智能体搭建任务书的关系

### 1.1 两类任务书的职责边界

| 对比项 | 智能体搭建任务书 | 本测试任务书 |
|---|---|---|
| 核心问题 | 要开发什么、按什么顺序开发 | 如何证明已开发内容符合要求 |
| 主任务编号 | TASK-101、TASK-102 等 | TTP-101、TTP-102 等 |
| 执行任务编号 | TASK-xxx | TTEST-xxx-xx |
| 测试用例编号 | 仅引用，不在搭建任务书中展开 | TTC-xxx-xxx |
| 产出 | 程序、配置、文档和业务能力 | 测试记录、证据、缺陷和验收结论 |
| 是否允许新增产品功能 | 是，但须按搭建任务书审批 | 否；发现新需求应退回产品需求流程 |

### 1.2 编号规则

- `TASK-101`：智能体搭建任务，含义为“建立项目代码结构”。
- `TTP-101`：针对 TASK-101 的测试任务书。
- `TTEST-101-01`：TTP-101 中的一项测试执行任务。
- `TTC-101-001`：TTP-101 中的一条具体测试用例。
- `BUG-101-001`：执行 TTP-101 时发现的缺陷。

测试任务不得使用 `TASK-xxx` 编号，防止被误认为智能体功能开发任务。

### 1.3 测试原则

1. **只验证已承诺范围**：不因数据库、合同解析等后续功能未实现而判定 TASK-101 失败。
2. **以可重复证据为准**：不能只以“开发者电脑能运行”作为通过依据。
3. **正常与异常并重**：既验证成功启动，也验证错误发生时能否定位且不会产生误导。
4. **安全默认**：任何客户资料、密钥、运行日志进入 Git，均视为阻断性问题。
5. **文档即产品的一部分**：新开发人员无法仅凭 README 启动，TASK-101 不得正式通过。

## 二、测试目标、范围与通过规则

### 2.1 测试目标

验证 TASK-101 交付的工程骨架是否满足以下条件：

- 新开发人员可以获取代码并按 README 完成本地启动；
- 后端健康检查接口真实可访问；
- 自动化测试框架可以运行并给出明确结果；
- 前端可以完成编译、构建并正确展示后端连接状态；
- 工程分层符合任务书约定，没有混淆 Capability、Orchestrator 和 Evidence 的职责；
- API Key、密码、客户资料、日志和本机构建产物不会进入代码仓库；
- GitHub Actions 可以在干净环境中复现后端检查。

### 2.2 测试范围

本次纳入：

- 根目录、后端、前端、测试、文档、模板、知识库、样例和日志目录；
- `.env.example`、`.gitignore`、依赖文件和 README；
- FastAPI 应用启动流程；
- `GET /api/v1/health`；
- `X-Trace-ID` 请求追踪基础逻辑；
- pytest、Ruff、TypeScript、Vite 构建；
- GitHub Actions 后端 CI；
- 前端后端在线/离线状态提示；
- 常见敏感文件和敏感字符串的仓库隔离。

### 2.3 明确排除范围

以下内容属于后续搭建任务，本次不得作为失败条件，也不得在测试结论中写成“已验证”：

- TASK-102 的数据库、文件上传与持久化；
- TASK-201 的 Project Context；
- TASK-202 的 Evidence Object Schema；
- Stage 3 的合同解析、收入确认和风险识别；
- Stage 4 的九态状态机、Dependency Graph 和 Execution Manifest；
- Stage 5 的 Evidence Lineage 和人工复核工作台；
- Stage 6 的正式 RBAC、底稿生成和 Replay / Re-run；
- 任何审计判断准确率和模型效果指标。

### 2.4 总体通过规则

测试结论按下列规则确定：

- **PASS**：全部 P0、P1 用例通过；P2 用例无影响启动或安全的缺陷。
- **PASS WITH CONDITIONS**：全部 P0 通过；存在有明确整改期限且不影响后续 TASK-102 开发的 P1/P2 问题。
- **FAIL**：任一 P0 用例失败，或多个 P1 问题使新开发人员无法稳定复现环境。

优先级定义：

- **P0 阻断**：无法安装/启动、健康检查不可用、测试框架不可运行、敏感信息进入仓库。
- **P1 重要**：README 关键步骤错误、异常不可定位、CI 不能复现、前端无法构建。
- **P2 一般**：非关键文案、展示或开发体验问题。

## 三、测试环境与角色

### 3.1 最低测试环境

至少执行以下两组环境：

| 环境编号 | 用途 | 最低要求 |
|---|---|---|
| ENV-101-A | 开发自动化环境 | Python 3.12、Node.js 20+、Git、可安装依赖 |
| ENV-101-B | 产品冷启动环境 | 一台未运行过本项目的 Windows 11 电脑 |

建议但不作为 V1.0 强制条件：增加一组 Ubuntu 或 GitHub Actions 环境，验证跨平台一致性。

### 3.2 测试角色

| 角色 | 责任 |
|---|---|
| 开发人员 | 执行自动化、修复缺陷、提供运行日志和提交记录 |
| 测试执行人 | 按用例执行，不依赖未写入 README 的口头说明 |
| 产品经理 | 确认范围、检查结果表达是否准确、签署最终结论 |
| 安全复核人 | 检查 Git 待提交文件及敏感信息扫描结果；MVP 可由开发兼任 |

### 3.3 测试前置条件

- 已取得 TASK-101 对应代码版本；
- 记录待测 commit SHA，不允许测试过程中静默更换版本；
- 工作区初始状态干净；
- 不使用真实客户合同、收入明细、银行流水或底稿；
- 所有安全测试数据均为人工构造的假数据；
- 测试报告中不得粘贴任何真实密钥。

# Test Stage C：后端 Smoke 与请求追踪

阶段目标：验证最短完整链路——应用启动、路由、配置、中间件、响应模型和关闭流程。

## Test Step C1：健康检查

### TTEST-101-07：正常访问健康检查接口

**执行步骤**

1. 启动后端。
2. 请求 `GET /api/v1/health`。
3. 记录 HTTP 状态、响应体和响应头。

**Acceptance Criteria**

- TTC-101-020（P0）：HTTP 状态为 200。
- TTC-101-021（P0）：`status` 为 `ok`。
- TTC-101-022（P1）：响应包含正确的 `service`、`version`、`environment`。
- TTC-101-023（P1）：响应不得声称数据库、模型或文件存储已经可用。

## Test Step C2：Trace ID

### TTEST-101-08：系统自动生成 Trace ID

**Acceptance Criteria**

- TTC-101-024（P1）：请求未携带 `X-Trace-ID` 时，响应自动返回非空 `X-Trace-ID`。
- TTC-101-025（P1）：对应请求日志包含相同 Trace ID。
- TTC-101-026（P0）：日志不包含请求正文、合同文本或交易数据。

### TTEST-101-09：保留调用方 Trace ID

**执行方法**

使用测试值 `test-trace-101-001` 请求健康检查接口。

**Acceptance Criteria**

- TTC-101-027（P1）：响应的 `X-Trace-ID` 与请求值完全一致。
- TTC-101-028（P1）：日志使用相同 Trace ID。

## Test Step C3：不存在的接口

### TTEST-101-10：访问未知路由

**Acceptance Criteria**

- TTC-101-029（P1）：返回 HTTP 404，而不是 500。
- TTC-101-030（P1）：服务进程保持运行，随后健康检查仍返回 200。
- TTC-101-031（P1）：404 响应和日志不暴露本地文件路径或堆栈。

## 五、缺陷管理

### 5.1 缺陷等级

| 等级 | 定义 | 示例 |
|---|---|---|
| S0 严重安全 | 可能泄露真实密钥或客户资料 | `.env` 或客户合同已进入 Git 历史 |
| S1 阻断 | TASK-101 核心目标不可用 | 无法安装、无法启动、健康检查失败 |
| S2 重要 | 可运行但不满足稳定交接 | README 缺关键步骤、CI 失败、前端无法构建 |
| S3 一般 | 不影响核心使用 | 非关键文案或展示问题 |

### 5.2 缺陷记录字段

每个缺陷至少记录：

- `bug_id`
- `test_case_id`
- 被测 commit SHA
- 测试环境
- 复现步骤
- 实际结果
- 预期结果
- 严重程度
- 截图或日志位置
- 责任人
- 修复 commit SHA
- 复测结果与时间

### 5.3 安全缺陷处理

发现真实密钥或客户资料时：

1. 立即停止上传和继续测试；
2. 不在缺陷截图、聊天或报告中复制敏感值；
3. 通知项目负责人撤销/轮换相关凭据；
4. 清理 Git 历史需要单独审批和受控操作；
5. 完成处置后重新执行全部安全测试。
