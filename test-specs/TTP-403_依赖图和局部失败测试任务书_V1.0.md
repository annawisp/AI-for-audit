## 2. TASK-403 验收标准

TASK-403 的核心目标是：建立程序与节点依赖图，使某个节点失败、阻塞或弃权时，只影响真正依赖该节点结论的后续节点；无依赖节点应继续执行，不得发生全局级联失败。

正式验收标准如下：

1. 系统应支持显式定义 procedure/node 级依赖关系，至少能表达：
   - 上游节点；
   - 下游节点；
   - 依赖原因；
   - 是否为硬依赖；
   - 依赖输入或输出字段。
2. 系统应提供可查询的依赖图结构，调用方可以查询：
   - 某个节点依赖哪些上游；
   - 某个节点失败会影响哪些下游；
   - 某个节点与其他节点是否无依赖关系。
3. 系统应支持并行分支依赖示例，例如：
   - 履约义务分支；
   - 交易价格分支；
   - 收款条件分支；
   - 合同层风险或收入确认分支。
4. 任一节点进入 `ABSTAINED` / `BLOCKED` / `PARTIAL` 等非完成状态后，仅停止或降级真正依赖该节点结论的后续节点。
5. 与失败节点无依赖关系的节点应继续保持可执行状态，例如 `READY`、`RUNNING`、`COMPLETED` 或其自身合理状态。
6. 依赖阻断必须可解释，至少说明：
   - 阻断源节点；
   - 受影响节点；
   - 依赖路径；
   - 阻断原因；
   - 建议恢复方式或补充资料方向。
7. 依赖路径必须可追溯，至少应提供 API、服务层查询或等价结构化输出；如有前端可视化则作为加分项，不作为本任务强制项。
8. TC-17 “仅合同”场景不得整体 Abstention：
   - 合同相关节点应继续执行；
   - 依赖收入明细、银行流水、应收数据的节点可进入 `BLOCKED` / `PARTIAL` / `ABSTAINED`；
   - 不依赖缺失资料的合同层节点不得被整体停止。
9. 局部失败不得破坏 TASK-402 的九态语义：
   - 不能把缺资料误写为 `NOT_PERFORMED`；
   - 不能把无依赖节点误写为 `BLOCKED`；
   - 不能伪造 `COMPLETED` 证据。
10. 局部失败不得提前实现 TASK-404 的完整 Execution Manifest；本任务只需提供依赖图、受影响节点、局部传播结果和解释。
11. 不破坏 TASK-101 至 TASK-402 既有接口和测试。
12. Foundation CI 中 `ruff` 与完整 `pytest` 应通过。

## 3. 建议实现边界

### 3.1 本任务应包含

- 依赖图数据结构或配置结构。
- 依赖关系注册、查询和解释能力。
- 局部失败传播算法。
- 对 `ABSTAINED`、`BLOCKED`、`PARTIAL` 等状态的下游影响计算。
- TC-17 仅合同场景下的局部可执行性判断。
- 与 TASK-402 procedure state 的集成或适配。

### 3.2 本任务不应包含

- 不生成完整项目级 Execution Manifest，该内容属于 TASK-404。
- 不做底稿输出。
- 不接入真实 LLM 或外部模型服务。
- 不实现 Review Workbench。
- 不把所有失败统一写成一个全局失败状态。
- 不要求前端必须完成图形化依赖图展示；结构化查询输出即可验收。

## 7. 通过/失败判定

- TASK-403 专项测试、完整后端回归测试、远端 Foundation CI 均通过：TASK-403 通过，可进入 TASK-404。
- 若 P02 `ABSTAINED` 导致无依赖的 P03/P04 整体停止：TASK-403 未通过。
- 若 TC-17 仅合同场景导致项目整体 `ABSTAINED`：TASK-403 未通过。
- 若依赖路径不可查询、不可解释或无法追溯阻断源：TASK-403 未通过。
- 若缺资料、业务不适用、人工不执行、AI 无法判断被混写成同一种状态：TASK-403 未通过。
- 若局部失败节点伪造 completed evidence：TASK-403 未通过。
- 若仅因外部 CI 环境、网络或缓存问题失败，应在测试报告中单独标记，不直接判定 TASK-403 功能失败。
