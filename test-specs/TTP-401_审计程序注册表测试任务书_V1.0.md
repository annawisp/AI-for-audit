# TTP-401 审计程序注册表测试任务书 V1.0

## 1. 测试对象

- 任务编号：TASK-401
- 能力名称：审计程序注册表（Procedure Registry）
- 所属阶段：Stage 4 Audit Procedure Orchestrator / Step 4.1 Procedure Registry
- 仓库：annawisp/AI-for-audit
- 依据文档：`build-specs/收入循环智能审计助手_搭建任务书_V1.0.md` 中 TASK-401。
- 测试范围：程序注册表配置模型、注册表加载与校验、程序依赖解释、Procedure 与 Capability 分离、版本化配置、API 或服务层查询能力、CI 基础质量门禁。

> 说明：仓库中存在 `docs/TASK-401-acceptance.md`，其对应第一轮整改任务书中的“重复解析隔离与 Parse Run 版本绑定”，不属于本测试任务书的验收口径。本测试任务书仅覆盖搭建任务书 Stage 4.1 的 TASK-401“审计程序注册表”。

## 2. 验收目标

TASK-401 应把审计程序从硬编码逻辑中抽离为可配置、可版本化、可解释的 Procedure Registry。系统应能够读取每个审计程序的输入、依赖、输出和执行策略，并解释程序当前为何处于 `READY`、`BLOCKED` 或 `PARTIAL`。当前阶段不要求真正执行完整审计程序状态机，也不要求实现 TASK-402 的九态状态流转。

## 3. 验收标准

1. 提供可维护的 Procedure Registry 配置来源，开发人员新增或调整程序依赖时不需要修改核心编排代码。
2. 每个 Procedure 配置至少包含：
   - `procedure_id`
   - `procedure_name`
   - `required_inputs`
   - `optional_inputs`
   - `dependent_inputs`
   - `upstream_dependencies`
   - `output_schema`
   - `execution_policy`
   - `version`
3. Procedure 与 Capability 必须分离：Procedure 配置可声明调用一个或多个 Capability，但 Capability 本身不直接决定程序是否执行。
4. 注册表加载时应进行结构校验，缺少必填字段、重复 `procedure_id`、引用不存在的 Capability 或非法执行策略时，应返回受控错误，不允许静默忽略或运行期 500。
5. 系统应能解释某个 Procedure 当前为何为 `READY`、`BLOCKED` 或 `PARTIAL`：
   - 必需输入齐备且上游依赖满足时为 `READY`；
   - 必需输入缺失或上游依赖未满足时为 `BLOCKED`；
   - 必需输入基本可用但可选/依赖输入部分缺失，或仅能局部执行时为 `PARTIAL`。
6. Procedure 配置应支持版本化，响应或服务返回中能够看到当前配置版本；同一程序版本变化应可被测试识别。
7. Registry 不得破坏 TASK-101 至 TASK-305 既有接口、证据对象、文档解析、合同抽取、收入确认、收入风险识别和数据核对能力。
8. Foundation CI 中 `ruff` 与完整 `pytest` 应通过。

## 4. 建议实现边界

### 4.1 本任务应包含

- 新增 Procedure Registry 配置文件或等价持久化结构。
- 新增 Pydantic schema 或服务层模型，对注册表配置进行稳定校验。
- 新增注册表加载服务，例如 `app/orchestrator/procedure_registry.py`。
- 新增查询接口或服务函数，用于列出程序、查询程序详情、解释 readiness。
- 至少提供收入循环相关的基础 Procedure 配置，例如：
  - 合同要素提取相关程序；
  - 收入确认分析相关程序；
  - 收入风险识别相关程序；
  - 数据核对与异常检测相关程序。

### 4.2 本任务不应包含

- 不实现完整九态状态机（属于 TASK-402）。
- 不实现程序实际执行编排、自动调度或批量运行。
- 不接入真实 LLM 或外部服务。
- 不把 Capability 的业务判断结果硬编码成 Procedure 是否可执行的唯一依据。

## 5. 自动化测试用例

| 用例编号 | 优先级 | 场景 | 输入/操作 | 期望结果 |
| --- | --- | --- | --- | --- |
| TTP-401-001 | P0 | 注册表可加载 | 启动服务或直接调用注册表加载函数 | 返回非空程序列表；每个程序包含必填字段 |
| TTP-401-002 | P0 | Procedure 配置字段完整性 | 检查所有内置 Procedure | 均包含 `procedure_id/procedure_name/required_inputs/optional_inputs/dependent_inputs/upstream_dependencies/output_schema/execution_policy/version` |
| TTP-401-003 | P0 | `procedure_id` 唯一 | 构造或扫描注册表配置 | 不允许重复；重复时返回稳定错误码，例如 `duplicate_procedure_id` |
| TTP-401-004 | P0 | Procedure 与 Capability 分离 | 检查 Procedure 配置中的 capability 引用 | 一个 Procedure 可引用多个 Capability；Capability 配置/实现不直接充当 Procedure 注册表 |
| TTP-401-005 | P0 | 缺少必填输入时解释为 BLOCKED | 构造缺少 `required_inputs` 的 readiness 上下文 | 返回 `status=BLOCKED`，解释中列出缺失输入 |
| TTP-401-006 | P0 | 必需输入齐备时解释为 READY | 构造必需输入和上游依赖均满足的上下文 | 返回 `status=READY`，解释中说明满足项 |
| TTP-401-007 | P1 | 部分资料可用时解释为 PARTIAL | 构造必需输入可用但 dependent/optional 输入部分缺失的上下文 | 返回 `status=PARTIAL`，解释中列出可执行部分和限制事项 |
| TTP-401-008 | P1 | 上游依赖未完成 | 构造 `upstream_dependencies` 未满足的上下文 | 返回 `status=BLOCKED`，解释中列出未满足上游程序或证据 |
| TTP-401-009 | P1 | 非法 Capability 引用 | 构造引用不存在 capability 的配置 | 注册表校验失败，返回稳定错误码，例如 `capability_not_found` |
| TTP-401-010 | P1 | 非法执行策略 | 构造非法 `execution_policy` | 注册表校验失败，返回稳定错误码，例如 `invalid_execution_policy` |
| TTP-401-011 | P1 | 配置版本可见 | 查询程序详情 | 响应包含 `version`；版本字段非空且格式稳定 |
| TTP-401-012 | P1 | 不修改核心代码即可调整依赖 | 在测试中加载一份临时 registry fixture，调整某程序依赖 | 加载结果和 readiness 解释随配置变化，不需要改业务代码 |
| TTP-401-013 | P0 | 回归测试 | 执行 TASK-101 至 TASK-305 既有后端测试 | 既有测试不被破坏 |
| TTP-401-014 | P0 | 远端 Foundation CI | 推送后触发 GitHub Actions | `ruff` 与 `pytest` 全部通过 |

## 8. 通过/失败判定

- 全部 TASK-401 专项测试通过，且完整后端回归测试通过：TASK-401 通过，可进入 TASK-402。
- 若 Registry 可加载但 readiness 解释不稳定、缺少缺失项明细或将缺失资料误判为审计师未执行，应判定 TASK-401 未通过。
- 若新增 Procedure 仍需要修改核心编排代码才能调整依赖，应判定 TASK-401 未通过。
- 若 Procedure 与 Capability 边界混淆，例如由 Capability 直接决定程序状态且注册表不可解释，应判定 TASK-401 未通过。
- 若仅因外部 CI 环境、冷启动环境或与 TASK-401 无关的历史问题失败，应在测试报告中单独标记，不直接判定 TASK-401 功能失败。
