# TTP-302 合同要素提取 Capability 测试任务书 V1.0

> 对应搭建任务：TASK-302 合同要素提取 Capability  
> 所属阶段：Stage 3 文档处理与审计能力模块 / Step 3.2 合同与收入审计核心能力  
> 测试目标：验证系统能基于 TASK-301 解析结果，从合同中提取收入审计关键要素，并形成可追溯、可复核、符合统一 Evidence Object Schema 的结构化输出。

## 1. 测试范围

本测试任务书覆盖 TASK-302 的能力验收，不覆盖收入确认分析、风险识别、底稿生成或人工复核台 UI。

### 1.1 包含范围

- 基于 TASK-301 document chunks 执行合同要素提取。
- 提取收入审计相关合同字段。
- 为每个字段保留原文来源位置和证据文本。
- 字段级支持证据不足、缺失、不适用、冲突等状态。
- 将提取结果转换为统一 Evidence Object 或兼容 Evidence Object 的结构。
- 局部字段失败不导致整个合同提取失败。
- 合同级 capability run 状态可解释。

### 1.2 不包含范围

- 不判断最终收入确认是否正确。
- 不输出审计结论或底稿。
- 不要求完成 TASK-303 收入确认分析。
- 不要求完成 TASK-304 风险识别。
- 不要求实现人工复核台界面。
- 不强制要求真实 LLM 调用；可以使用 rule、heuristic、mock LLM 或可替换的 extractor。

## 2. 被测对象

TASK-302 应至少提供一种可测试入口，例如 API、service function、capability runner 或等价接口。

建议接口形态：

- 输入：`project_id`、`document_id`，可选 `parse_run_id`。
- 依赖：TASK-301 产生的 `document_chunks` 或等价结构。
- 输出：合同要素字段结果、字段级证据来源、合同级执行状态、Evidence Object 或 Evidence-compatible payload。

若实际实现采用不同接口，测试应以“功能等价”为准，但必须能验证本任务书列出的验收标准。

## 3. 核心验收标准

### AC-302-01 可提取核心合同要素

系统应至少支持以下字段的识别与结构化输出：

- 合同主体：客户、供应商或服务提供方；
- 合同期间：合同开始日期、结束日期、服务期间或交付期间；
- 商品或服务内容；
- 履约义务；
- 交易价格或合同金额；
- 收款条件或付款条款；
- 验收条件；
- 特殊条款：退款、折扣、可变对价、终止条款、续约、重大限制等。

通过标准：

- 标准合同样本中，上述字段应尽可能被提取。
- 未出现的字段不得编造。
- 每个字段必须有字段状态。

### AC-302-02 字段结果可回溯原文

每个成功提取的字段必须保留来源信息，至少包含：

- `document_id`；
- `chunk_id` 或 `source_locator`；
- 页码、段落号、行号、sheet-row 中至少一种定位信息；
- `source_text` 或 `evidence_excerpt`；
- `extraction_method`，例如 `rule`、`heuristic`、`llm`、`manual_seed`。

通过标准：

- 审计人员可以从字段值回到原合同文字。
- 来源位置不得为空或泛化为“合同全文”。

### AC-302-03 字段级 Field Abstention

字段证据不足时，系统必须支持字段级降级，不得让整个 TASK-302 失败。

字段状态建议至少支持：

- `EXTRACTED`：已提取；
- `ABSTAINED`：证据不足，系统不判断；
- `MISSING_IN_DOCUMENT`：合同中未发现该字段；
- `NOT_APPLICABLE`：该字段对当前合同明显不适用；
- `CONFLICTING_EVIDENCE`：不同条款存在冲突，需人工复核。

通过标准：

- 合同缺少验收条款时，只标记验收条件字段缺失或 abstained。
- 其他可提取字段仍正常输出。

### AC-302-04 区分字段缺失与资料未提供

系统必须区分：

- 合同已提供，但合同内没有某字段；
- 合同文件未提供；
- 合同存在但 TASK-301 未完成解析；
- TASK-301 上游解析 BLOCKED。

通过标准：

- “合同中没有收款条件”不得等同于“合同未上传”。
- `document_id` 不存在时应返回输入缺失或 not found 类状态。
- 上游解析失败时应返回 `BLOCKED` 或 `DEPENDENCY_NOT_READY` 类状态。

### AC-302-05 输出符合统一 Evidence Object Schema

TASK-302 输出必须能转换为 TASK-202 定义的 Evidence Object。

至少应包含：

- `evidence_id`；
- `project_id`；
- `procedure_id` 或 `capability_id`；
- `document_id`；
- `source`；
- `extracted_value`；
- `conclusion`；
- `execution_status`；
- `node_status`；
- `judgment_status`；
- `confidence` 或 `confidence_level`；
- `confidence_basis`；
- `timestamp`；
- `reviewer` 可为空；
- `trace_id` 或 `run_id`。

通过标准：

- 合同要素提取结果可被后续 TASK-303 消费。
- 不得输出与 Evidence Object 完全割裂的私有结构。

### AC-302-06 合同级 Capability 状态可解释

TASK-302 整体运行应有 capability-level 状态。

建议状态：

- `COMPLETED`：关键字段大部分成功提取；
- `PARTIAL`：部分字段成功，部分字段 abstained 或 missing；
- `ABSTAINED`：合同内容不足以提取任何有效字段；
- `BLOCKED`：依赖失败、合同无法读取、document_parse 未完成或数据结构异常；
- `REQUIRES_REVIEW`：存在冲突或低置信度，需要人工复核。

通过标准：

- 只提取出主体和金额时，应为 `PARTIAL`，不是整体失败。
- 上游 TASK-301 BLOCKED 时，应为 `BLOCKED` 或等价依赖失败状态。

### AC-302-07 正确衔接 TASK-301 Document Processor

TASK-302 应基于 TASK-301 的 chunks 工作。

通过标准：

- 能读取 document chunks。
- 能保留 chunk 的 `source_locator`。
- 若 document 没有 parse run 或 chunk，应返回明确依赖状态。
- 不应重复实现文件上传或基础文件解析逻辑。

### AC-302-08 局部字段失败不影响其他字段

单个字段无法提取、格式异常或存在冲突时，不应影响其他字段。

通过标准：

- 金额无法识别时，主体、期间、服务内容仍可提取。
- 日期格式异常时，其他字段仍可提取。
- 某字段冲突时，只将该字段标记为 `CONFLICTING_EVIDENCE` 或 `REQUIRES_REVIEW`。

### AC-302-09 置信度与依据说明

每个字段应包含：

- `confidence` 或 `confidence_level`；
- `confidence_basis`；
- `extraction_reason` 或等价说明；
- `source_text` 或 `evidence_excerpt`。

通过标准：

- 字段值不能只有结论，必须解释依据。
- 低置信度字段应能触发 review 或标记为需复核。

## 4. 测试数据要求

测试数据应尽量使用可控、脱敏、最小化样本，不包含真实客户敏感信息。

建议准备以下合同样本：

| 样本编号 | 样本名称 | 目的 |
|---|---|---|
| S302-01 | 标准服务合同 | 覆盖主体、期间、服务、价格、付款、验收条件 |
| S302-02 | 字段缺失合同 | 缺少验收条件或收款条件 |
| S302-03 | 特殊条款合同 | 包含折扣、退款、终止、可变对价等 |
| S302-04 | 多履约义务合同 | 包含多个服务或交付义务 |
| S302-05 | 低质量解析合同 | chunks 存在但文本不完整 |
| S302-06 | 字段冲突合同 | 不同段落金额或期间冲突 |
| S302-07 | 无合同输入 | document_id 不存在或未上传合同 |
| S302-08 | 上游 BLOCKED 合同 | TASK-301 解析失败或无 chunks |

## 5. 测试用例设计

### TC-302-01 标准合同字段完整提取

前置条件：

- 已创建 project。
- 已上传标准合同。
- TASK-301 已生成 document chunks。

步骤：

1. 调用 TASK-302 合同要素提取入口。
2. 查询提取结果或 Evidence Object。
3. 检查字段、来源、状态、置信度。

预期结果：

- capability 状态为 `COMPLETED` 或等价成功状态。
- 合同主体、期间、服务内容、履约义务、交易价格、收款条件、验收条件均有结构化输出。
- 每个成功字段均有 source_locator 和 evidence_excerpt。
- 输出符合 Evidence Object Schema。

### TC-302-02 字段缺失时字段级 abstention

前置条件：

- 合同中不包含验收条件或收款条件。
- TASK-301 已成功解析。

步骤：

1. 运行 TASK-302。
2. 检查缺失字段状态。
3. 检查其他字段是否正常提取。

预期结果：

- 缺失字段状态为 `MISSING_IN_DOCUMENT` 或 `ABSTAINED`。
- 其他字段仍为 `EXTRACTED`。
- capability 状态为 `PARTIAL`，不得为整体失败。

### TC-302-03 特殊条款识别

前置条件：

- 合同包含退款、折扣、终止、续约、可变对价等特殊条款之一或多个。

步骤：

1. 运行 TASK-302。
2. 检查 special_terms 字段。
3. 检查特殊条款来源定位。

预期结果：

- special_terms 中包含识别出的特殊条款类型和文本。
- 每条特殊条款均可追溯至原文 chunk。
- 低置信度特殊条款应标记 review 或 confidence_level 为 low/medium。

### TC-302-04 多履约义务合同

前置条件：

- 合同包含两个或两个以上商品/服务或交付义务。

步骤：

1. 运行 TASK-302。
2. 检查 performance_obligations 字段。

预期结果：

- 可输出多个履约义务。
- 每个履约义务有独立来源位置。
- 不应将多个义务错误合并为单一不可拆分文本。

### TC-302-05 低质量 chunks 局部提取

前置条件：

- TASK-301 产生 chunks，但部分文本缺失或不完整。

步骤：

1. 运行 TASK-302。
2. 检查可提取字段与不可提取字段状态。

预期结果：

- 可识别字段正常输出。
- 不足字段为 `ABSTAINED` 或 `MISSING_IN_DOCUMENT`。
- capability 状态为 `PARTIAL` 或 `ABSTAINED`，不得出现未捕获异常。

### TC-302-06 无合同输入

前置条件：

- project 存在，但 document_id 不存在，或未上传合同。

步骤：

1. 使用不存在的 document_id 调用 TASK-302。

预期结果：

- 返回明确错误或状态，例如 `document_not_found`、`INPUT_NOT_PROVIDED`。
- 不得生成虚假 Evidence Object。
- 不得将该情况标记为合同字段缺失。

### TC-302-07 上游 TASK-301 未完成或 BLOCKED

前置条件：

- document 存在，但无 parse run、无 chunks，或 TASK-301 状态为 BLOCKED。

步骤：

1. 调用 TASK-302。

预期结果：

- TASK-302 返回 `BLOCKED`、`DEPENDENCY_NOT_READY` 或等价状态。
- failure_reason 指向上游解析未完成或失败。
- 不得重新解析原始文件绕过 TASK-301。

### TC-302-08 字段冲突识别

前置条件：

- 合同不同段落对金额、期间或付款条件存在冲突。

步骤：

1. 运行 TASK-302。
2. 检查冲突字段。

预期结果：

- 冲突字段状态为 `CONFLICTING_EVIDENCE` 或触发 `REQUIRES_REVIEW`。
- 输出至少两个冲突来源。
- 其他无冲突字段正常提取。

### TC-302-09 Evidence Object Schema 校验

前置条件：

- TASK-302 已产生提取结果。

步骤：

1. 读取 Evidence Object 或 Evidence-compatible payload。
2. 校验必填字段和状态字段。

预期结果：

- 包含 evidence_id、project_id、document_id、source、extracted_value、execution_status、node_status、judgment_status、confidence_basis、timestamp 等字段。
- `extracted_value` 中包含合同要素结构化结果。
- 后续 TASK-303 可以直接消费该输出。

### TC-302-10 Trace 与错误处理

前置条件：

- 构造正常输入和异常输入各一组。

步骤：

1. 运行正常提取。
2. 运行异常输入提取。
3. 检查响应和日志/trace。

预期结果：

- 关键请求包含 trace_id 或 run_id。
- 异常不会导致服务进程崩溃。
- 错误码和 failure_reason 可解释。

## 6. 自动化测试建议

建议新增测试文件：

- `backend/tests/test_task302_contract_extraction.py`

建议覆盖层级：

- service-level unit tests：字段抽取、字段状态、冲突识别；
- API integration tests：project/document/chunks → TASK-302 → Evidence Object；
- dependency tests：无 chunks、上游 BLOCKED、document_id 不存在；

```bash

pytest
npm run build
```

## 7. 通过 / 失败判定

### 7.1 通过条件

满足以下条件可判定 TASK-302 通过：

- 所有新增 TASK-302 自动化测试通过。
- 既有 Foundation CI 全部通过。
- 标准合同能提取核心字段，并保留来源定位。
- 字段缺失、资料未提供、上游解析失败可以区分。
- 输出符合 Evidence Object Schema。
- 局部字段失败不会导致整体崩溃。

### 7.2 失败条件

出现以下任一情况应判定失败：

- 字段值无来源定位。
- 字段缺失时编造内容。
- 单个字段缺失导致整个 capability 失败。
- 合同未提供与字段缺失混淆。
- 输出无法转换为 Evidence Object。
- 上游 TASK-301 未完成时 TASK-302 仍伪造结果。
- 远端 Foundation CI 失败。

## 9. 与后续任务的边界

- TASK-302 的输出是 TASK-303 收入确认分析的输入。
- TASK-302 不判断收入确认是否恰当。
- TASK-302 不生成最终审计结论。
- TASK-302 应为 TASK-501 Evidence/Data Lineage 保留足够来源信息。
- TASK-302 的字段级 abstention 应为 TASK-402 九态状态机和 TASK-403 局部失败提供基础。
