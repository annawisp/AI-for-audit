# TTP-402 程序状态机测试任务书 V1.0

## 1. 测试对象

- 任务编号：TASK-402
- 能力名称：程序状态机（Execution Status State Machine）
- 所属仓库：annawisp/AI-for-audit
- 测试范围：程序执行状态模型、状态转换规则、状态转换审计日志、状态解释、与 Evidence Object 的一致性、API/服务层查询能力、Foundation CI 质量门禁。

## 2. 验收目标

TASK-402 应在 TASK-401 Procedure Registry 基础上，实现审计程序执行状态机，并明确支持以下九种状态：

```text
NOT_STARTED / READY / RUNNING / COMPLETED / PARTIAL / NOT_APPLICABLE / NOT_PERFORMED / BLOCKED / ABSTAINED
```

系统应能根据审计师指令、项目配置和系统事实共同驱动程序状态；AI 或规则引擎不得自行认定“审计师没有执行程序”。状态转换必须可解释、可追溯，并与 Evidence Object 的执行状态、节点状态、判断状态保持一致。

## 3. 验收标准

1. 显式定义九态 Execution Status，状态名称稳定且大小写一致。
2. 支持基于 TASK-401 registry 初始化项目下的 procedure execution states。
3. 支持 `NOT_STARTED -> READY -> RUNNING -> COMPLETED` 等合法路径。
4. 缺少必需输入或上游依赖不足时，应进入 `BLOCKED`，并记录阻塞原因。
5. 只有部分输入或部分证据满足时，应进入 `PARTIAL`。
6. 审计师或项目配置明确不执行时，才能进入 `NOT_PERFORMED`。
7. AI/系统不得自行将程序置为 `NOT_PERFORMED`。
8. 证据不足、字段不足或置信度不足时，应支持 `ABSTAINED`，并记录 abstention 层级和原因。
9. 完成状态应关联 Evidence；`BLOCKED` / `ABSTAINED` 不得伪造完成证据。
10. 每次状态转换应写入审计日志，至少包括前状态、后状态、触发方、原因、时间戳和 trace/run 标识。
11. 不提前实现 TASK-403 的依赖图局部失败传播，也不提前实现 TASK-404 的完整 Execution Manifest。
12. 不破坏 TASK-101 至 TASK-401 既有接口和测试。
13. Foundation CI 中 `ruff` 与完整 `pytest` 应通过。

## 6. 通过/失败判定

- TASK-402 专项测试、完整后端回归测试、远端 Foundation CI 均通过：TASK-402 通过，可进入下一部分。
- 若九态不完整、非法跳转未被拒绝、`NOT_PERFORMED` 可由 AI/系统自动生成、状态转换无审计日志，或 Evidence Object 状态语义与程序状态冲突：TASK-402 未通过。
- 若仅为外部 CI 环境问题导致失败，应在测试报告中单独标记，不直接判定 TASK-402 功能失败。
