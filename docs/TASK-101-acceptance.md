## 4. 产品经理应掌握的背后逻辑

### 为什么此时只有一个健康检查接口

健康检查是最小“竖切”：它同时验证路由、配置、应用启动、中间件、响应模型和测试链路。先让这条最短链路闭环，后续增加数据库或文件服务时，出错位置才容易判断。

### 为什么目录提前预留，但不写空业务逻辑

`capabilities`、`orchestrator`、`evidence` 提前确定边界，是为了避免后续把合同解析、状态判断和证据输出混在一个 Agent 里。只保留包和职责说明，不伪造未完成的实现，也让任务进度可审计。

### 为什么日志不记录请求正文

审计资料高度敏感。当前追踪层只记录 trace ID、方法、路径和状态码。这样后续能定位一次运行，又不会默认把合同或交易明细复制进日志。

### 为什么前端现在只是连接状态页

TASK-101 的前端目标是证明工程和 API 连接方式成立。复核台在 Evidence、状态机和 Review 数据结构定义后再开发，否则界面会反向固化尚未确认的数据模型。

## 5. 进入 TASK-102 前的产品决策

下一步需要确认的第一个重要决策是 MVP 的运行形态：

1. **单机本地原型（推荐）**：SQLite + 本地受控文件目录，搭建快，适合先验证流程；之后迁移 PostgreSQL/对象存储。
2. **从一开始按多人环境建设**：PostgreSQL + MinIO/企业对象存储，更接近生产，但部署和权限成本更高。

推荐先选 1，但在代码层使用存储接口隔离，避免未来迁移时修改审计业务逻辑。
