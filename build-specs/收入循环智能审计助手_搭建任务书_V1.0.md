# 一、项目定位与任务书使用方式

本任务书用于把现有收入循环智能审计助手需求，转换为可执行的软件搭建计划。任务书采用“Stage → Step → Task → Acceptance Criteria”四级结构：Stage 管项目阶段与里程碑，Step 管阶段内建设顺序，Task 管具体开发事项，Acceptance Criteria 用于业务和技术联合验收。

## 1.1 产品定位

系统定位为“AI + Rules + Evidence + Human-in-the-loop”的审计智能系统，不以“多个 Agent 串行执行”作为产品架构。核心是审计程序编排、局部依赖、程序状态管理、证据可追溯和人工复核。

- 系统应支持审计程序可选执行与部分执行。

- 资料不完整时，不得导致整个系统或整条流程整体失败。

- AI 不得把“资料未提供”自动解释为“审计师未执行程序”。

- 所有重要审计判断应保留证据来源、状态、置信依据和人工复核痕迹。

- 底稿输出必须基于已确认的证据和实际执行范围，并强制输出 Coverage & Limitations。

## 1.2 总体架构

建议总体架构分为九层：

- L0 安全、权限、日志、版本与可追溯底座

- L1 Project Context 与文件存储

- L2 文档与数据处理

- L3 审计数据模型与 Evidence Object

- L4 Rules / Knowledge / LLM 基础能力

- L5 Audit Procedure Orchestrator

- L6 Audit Capability Modules

- L7 Evidence Assembly / Data Lineage / Review

- L8 底稿与输出

其中最关键的不是单一大模型，而是“统一数据模型 + 审计程序编排器 + Evidence/Data Lineage”。这三部分先搭稳，再逐步扩展更多审计能力。

# Stage 1：基础工程与运行底座

阶段目标：先建立一个可持续开发、可测试、可部署、可追踪的工程骨架。

## Step 1.1：建立代码仓库与基础工程

### TASK-101 建立项目代码结构

**目标：**建立前后端分离、能力模块独立、测试和日志完整的项目骨架。

**主要工作：**

- 建立 backend、frontend、tests、docs、templates、knowledge_base、sample_data、logs 等目录。

- 后端采用清晰的 api / services / models / schemas / orchestrator / capabilities / evidence 分层。

- 为每个核心能力预留 inputs、outputs、logs、tests 或对应等价结构。

- 建立环境变量模板、依赖管理和本地开发说明。

**交付物：**

- GitHub Repository

- README

- 基础目录结构

- 依赖文件

- 环境变量模板

**Acceptance Criteria：**

- 新开发人员 clone 仓库后，可按 README 完成本地启动。

- 后端健康检查接口可访问。

- 单元测试框架可运行。

- 仓库中不包含 API Key、密码、客户资料等敏感信息。

## Step 1.2：搭建基础服务

### TASK-102 基础 API、数据库与文件存储

**目标：**为后续项目、文件、程序状态、证据对象提供稳定存储和访问接口。

**主要工作：**

- 建立 Project、Document、Procedure、Evidence、Review、Run 等基础数据表或等价持久化结构。

- 实现文件上传、文件元数据登记、文件状态查询。

- 实现统一日志接口和错误码体系。

- 为后续 Replay / Re-run 预留版本字段。

**Acceptance Criteria：**

- 可以创建项目、上传文件、查询项目和文件。

- 所有关键请求均有 trace/run 标识。

- 数据库异常和文件异常不会直接导致服务进程崩溃。

# Stage 2：审计数据与证据模型

阶段目标：先定义系统理解审计项目所需的统一数据对象，避免不同模块各自输出不可兼容结果。

## Step 2.1：建立 Project Context

### TASK-201 Project Context MVP

**目标：**定义项目级最小必要信息，作为所有审计能力的统一上下文。

**主要工作：**

- MVP 1.0 仅保留基础信息、审计期间、重要性、收入模式、合同等核心上下文。

- 收入明细、客户名单、应收、银行流水等扩展内容作为后续版本或可选输入。

- Project Context 不应成为项目启动的强制“大而全”数据包。

**Acceptance Criteria：**

- 只提供基础信息和合同时也能创建并启动项目。

- 缺少扩展数据不会阻塞全部程序。

- Project Context 版本变化可追踪。

## Step 2.2：建立统一 Evidence Object

### TASK-202 Evidence Object Schema

**目标：**建立所有规则、AI判断、人工复核和底稿输出共同使用的统一证据对象。

**主要工作：**

- 固定 Schema，字段至少覆盖 evidence_id、project_id、procedure_id、source、extracted_value、conclusion、execution_status、node_status、judgment_status、confidence、reviewer、timestamp 等。

- node_status 与 judgment_status 独立维护。

- 支持 model_confidence、confidence_level、confidence_basis。

- 禁止各能力模块自定义互不兼容的输出结构。

**Acceptance Criteria：**

- 任一能力模块的核心结果都能转换成 Evidence Object。

- AI_GENERATED / PENDING_REVIEW / CONFIRMED / MODIFIED / REJECTED / NEED_MORE_EVIDENCE 可正确流转。

- 历史 Evidence Object 可按版本读取。

## Step 2.3：数据标准化与质量分级

### TASK-203 Normalization & Dataset Quality

**目标：**保证原始值、标准值和转换规则可追溯，并对结构化数据质量进行分级。

**主要工作：**

- 金额、日期、币种等同时保存 raw_value 与 standard_value。

- 记录 normalization_rule。

- 建立 Dataset Quality Score 或等价分级机制。

- 避免“整批拒入”的二元逻辑。

**Acceptance Criteria：**

- 审计人员可以看到原始值和标准值的对应关系。

- 低质量数据允许进入“部分可分析”而不是直接整批失败。

- 质量状态会影响后续 Procedure 的 READY/PARTIAL/ABSTAINED 判断。

# Stage 3：文档处理与审计能力模块

阶段目标：建立可以独立运行、独立测试、独立停用的 Audit Capability，而不是先做固定串行 Agent 流程。

## Step 3.1：Document Processor

### TASK-301 文档与表格解析

**目标：**把 PDF、DOCX、XLSX、CSV、TXT 等资料解析成可引用、可定位的结构化内容。

**主要工作：**

- 实现文本、表格和基础元数据提取。

- 仅在确有需要时使用 OCR fallback。

- 保存 document_id、页码、sheet、行号、段落号、原始文本等定位信息。

- 解析失败需返回明确状态和原因。

**Acceptance Criteria：**

- 一份合同中的关键条款可被定位回具体页或段落。

- Excel 中的关键数据可追溯到具体 sheet/row。

- 损坏文件进入 BLOCKED，而不是产生虚假解析结果。

## Step 3.2：合同与收入审计核心能力

### TASK-302 合同要素提取 Capability

**目标：**从合同中提取收入审计所需关键要素，并形成 Evidence Object。

**主要工作：**

- 提取合同主体、期间、商品/服务、履约义务、交易价格、收款条件、验收条件、特殊条款等。

- 每个关键字段保留来源位置。

- 字段级证据不足时支持 Field Abstention。

**Acceptance Criteria：**

- 关键字段可回溯原文。

- 字段缺失与未提供资料能够区分。

- 输出符合统一 Evidence Object Schema。

### TASK-303 收入确认分析 Capability

**目标：**基于合同要素、Project Context 及可选收入记录完成收入确认相关分析。

**主要工作：**

- 采用“触发 → 分析 → 结论”的三态判断结构。

- 每个判断节点可进入人工 Review。

- 不要求收入明细必须存在；仅在需要做差异分析时调用相关记录。

**Acceptance Criteria：**

- 仅合同场景可完成合同层面的收入确认分析。

- 缺少收入记录时，不影响已具备证据的其他节点。

- 结论必须带 Coverage、Limitations 和影响说明。

### TASK-304 收入风险识别 Capability

**目标：**采用 Rules + LLM Judgment 双轨机制识别收入风险。

**主要工作：**

- 规则用于阈值、日期、金额比较、重复交易、截止性、异常组合等高频风险。

- LLM 用于合同语义、商业实质和非标准条款判断。

- 风险状态至少支持 COMPLETE / PARTIAL / INSUFFICIENT_DATA。

- 规则覆盖率与模型召回率分开评价。

**Acceptance Criteria：**

- 预定义高频风险信号均进入规则库和测试。

- 仅合同场景也能输出合同相关风险，不整体失败。

- 无法计算的信号不进入评分分母，并显示 Coverage Ratio。

## Step 3.3：数据核对与异常分析

### TASK-305 数据核对与异常检测 Capability

**目标：**在相关资料存在时执行合同、收入、应收、回款等数据核对和异常筛选。

**主要工作：**

- 支持合同与收入记录匹配、应收匹配、回款匹配、截止分析、异常交易筛选。

- 统计方法如 Benford 仅作为风险信号，不直接形成审计结论。

- 未提供某类数据时，只影响依赖该数据的能力。

**Acceptance Criteria：**

- 不同数据组合可以独立运行。

- 匹配结果包含 link_method 与 link_confidence。

- 无法匹配与资料未提供状态分开记录。

# Stage 4：Audit Procedure Orchestrator

阶段目标：实现能力驱动、局部依赖、可选执行、部分执行的审计程序编排机制。此阶段是整个系统的核心。

## Step 4.1：Procedure Registry

### TASK-401 审计程序注册表

**目标：**把每个审计程序的输入、依赖、输出和执行策略显式配置化。

**主要工作：**

- 定义 procedure_id、procedure_name、required_inputs、optional_inputs、dependent_inputs、upstream_dependencies、output_schema、execution_policy。

- 审计程序与 Capability 分离：一个 Procedure 可调用一个或多个 Capability。

- 程序配置可版本化。

**Acceptance Criteria：**

- 开发人员不改核心代码即可新增或调整程序依赖配置。

- 系统可以解释某程序为何 READY、BLOCKED 或 PARTIAL。

## Step 4.2：九态 Execution Status

### TASK-402 程序状态机

**目标：**实现 NOT_STARTED / READY / RUNNING / COMPLETED / PARTIAL / NOT_APPLICABLE / NOT_PERFORMED / BLOCKED / ABSTAINED 九态。

**主要工作：**

- 明确区分 NOT_PERFORMED、NOT_APPLICABLE、BLOCKED、ABSTAINED。

- 程序状态由审计师、项目配置和系统事实共同驱动；AI 不得自行认定“审计师没做程序”。

- 支持字段级、节点级、程序级 Abstention。

**Acceptance Criteria：**

- 状态转换有明确规则和审计日志。

- 资料缺失、系统错误、业务不适用、人工不执行不会混为同一状态。

- 状态与 Evidence Object 保持一致。

## Step 4.3：Dependency Graph 与局部失败

### TASK-403 依赖图和 Local Failure

**目标：**建立程序与节点依赖图，使某节点失败只影响真正依赖它的后续节点。

**主要工作：**

- 建立履约义务、交易价格、收款条件等并行分支依赖示例。

- 实现任一节点 Abstention 后，仅停止依赖该节点结论的后续节点。

- 无依赖节点继续执行。

**Acceptance Criteria：**

- P02 ABSTAINED 不会导致无依赖的 P03/P04 整体停止。

- 依赖路径可视化或可查询。

- TC-17“仅合同”场景不整体 Abstention。

## Step 4.4：Execution Manifest

### TASK-404 项目执行清单

**目标：**记录本次 AI 实际执行、未执行、部分执行和无法执行的全部程序。

**主要工作：**

- 每次运行生成 Revenue Audit Execution Manifest。

- 记录程序、状态、输入、未执行/受限原因。

- Manifest 作为 Review Workbench 和底稿输出的必备组成。

**Acceptance Criteria：**

- 用户可以明确回答“本次 AI 做了什么、没做什么、为什么”。

- 底稿和导出结果包含 Execution Manifest。

- Manifest 与实际运行日志一致。

# Stage 5：Evidence、Data Lineage 与人工复核

阶段目标：让每个重要结论都能回到证据来源，并由审计人员完成确认、修改或拒绝。

## Step 5.1：Evidence Assembly 与 Data Lineage

### TASK-501 证据组装与血缘

**目标：**基于本次实际执行的程序形成可用证据链，而不是强制追求理想化完整链。

**主要工作：**

- 建立 Document → Segment → Field → Analysis → Judgment → Conclusion → Working Paper 的血缘链。

- Lineage Link 保存 link_method 与 link_confidence。

- 缺失环节区分 MISSING / NOT_PROVIDED / NOT_PERFORMED / NOT_APPLICABLE / UNMATCHED / LOW_CONFIDENCE。

**Acceptance Criteria：**

- 审计人员点击结论可追溯到原始资料位置。

- 部分证据链可以正常形成。

- 不同缺失语义不会统一显示为 Evidence Missing。

## Step 5.2：Knowledge Layer 与冲突管理

### TASK-502 知识库与规则库

**目标：**建立准则法规、事务所方法论和项目知识三类知识源。

**主要工作：**

- 知识源保留来源、版本、生效期间和优先级。

- 法规/方法论/客户制度不得混成单一不可解释知识库。

- 知识冲突不得静默覆盖，必须展示双方依据并交由专业负责人确定。

**Acceptance Criteria：**

- 系统可显示结论引用的知识来源。

- 冲突场景能生成 CONFLICT DETECTED 或等价状态。

- 人工选择结果被记录并可追溯。

## Step 5.3：Review Workbench

### TASK-503 人工复核台

**目标：**建立面向审计师的结构化复核界面，而不是仅提供聊天框。

**主要工作：**

- 顶部展示 Execution Manifest。

- 每个判断展示 AI Conclusion、Evidence、Confidence、Coverage、Limitations。

- 提供确认、修改、拒绝、需要更多证据操作。

- 所有复核动作保留 who / when / before / after / reason。

**Acceptance Criteria：**

- node_status=ANALYZED 与 judgment_status=PENDING_REVIEW 可同时存在。

- 人工修改后保留 AI 原判断。

- 每次输出都带 Coverage & Limitations。

## Step 5.4：Feedback Dataset

### TASK-504 AI Judgment Feedback & Evaluation

**目标：**沉淀 AI 原判断与人工复核差异，为后续 Prompt、规则和模型优化提供数据。

**主要工作：**

- 记录 AI 原判断、人工判断、修改内容、修改理由、证据、模型版本、Prompt版本、Rule版本、时间。

- 第一阶段以数据沉淀为主，不自动训练模型。

**Acceptance Criteria：**

- 可以按模型、Prompt、规则版本比较复核结果。

- 能统计确认率、修改率、拒绝率和需要更多证据比例。

# Stage 6：输出、治理与可复现

阶段目标：把已确认结果转化为可交付底稿，同时满足权限、安全、异常处理和历史可复现要求。

## Step 6.1：Working Paper Generator

### TASK-601 底稿生成

**目标：**基于已确认 Evidence、项目上下文、模板和实际执行范围生成审计底稿。

**主要工作：**

- 输入 = 已完成相关能力输出 + Evidence Chain + 内部模板 + Project Context。

- 不得假设所有上游 Agent/Capability 都存在。

- 优先 Evidence First，Narrative Second。

- 底稿强制包含 Coverage & Limitations。

**Acceptance Criteria：**

- 只有合同分析结果也能生成当前可生成部分的底稿。

- 未覆盖环节明确说明，不伪造结论。

- 底稿内容可追溯到 Confirmed Evidence。

## Step 6.2：Error & Exception Handling

### TASK-602 异常处理矩阵

**目标：**把技术错误、数据错误、输入不足、业务不适用、人工未执行、AI无法判断区分处理。

**主要工作：**

- 文件损坏 → BLOCKED；字段不足 → Field Abstention；节点证据不足 → Node Abstention；程序整体无法实施 → Procedure Abstention。

- 禁止自动 fallback 到未经证据支持的结论。

- 异常后优先局部降级，而不是全局停止。

**Acceptance Criteria：**

- 每类异常都有明确状态、提示和恢复路径。

- 随机资料子集不报错。

- 系统错误不被伪装为审计结论。

## Step 6.3：RBAC 与 Audit Trail

### TASK-603 权限与审计日志

**目标：**建立 Auditor / Senior / Manager / Partner/Admin 等角色权限和关键操作留痕。

**主要工作：**

- 权限覆盖上传、查看、运行程序、修改配置、审核判断、确认判断、导出底稿、管理知识库、查看日志。

- 关键变更保留 who / when / before / after / reason。

**Acceptance Criteria：**

- 未授权角色无法执行受限操作。

- 关键人工判断与配置修改均可追溯。

## Step 6.4：Replay / Re-run 与 Observability

### TASK-604 可复现与运行监控

**目标：**实现历史运行回放、同版本重跑和统一运行监控。

**主要工作：**

- Replay 保存并恢复 Input、Model Version、Prompt Version、Rule Version、Raw Output。

- Re-run 使用相同版本重新调用，只要求实质一致，不要求逐字一致。

- 日志至少记录 project_id、procedure_id、capability_id、model、prompt_version、token_usage、latency、execution_status、error_type、review_result。

**Acceptance Criteria：**

- 可以解释某程序某次为什么没有运行。

- Replay 可恢复历史原始输出。

- Re-run 与 Replay 在产品语义上清晰区分。

# Stage 7：MVP、测试与上线验收

阶段目标：用最小可行产品验证架构，而不是一开始把整个收入循环所有能力一次性做完。

## Step 7.1：MVP 1.0 范围

MVP 建议先验证以下链路：

1.  创建项目

2.  上传合同

3.  合同解析

4.  关键合同要素形成 Evidence Object

5.  收入确认相关判断

6.  收入风险信号

7.  人工 Review

8.  Evidence/Data Lineage

9.  Execution Manifest

10. Coverage & Limitations

11. 生成一份收入审计底稿

同时必须设计一个“故意不完整”的核心验收场景：仅上传合同，不提供收入明细和银行流水。

## Step 7.2：三类优先技术原型

### TASK-701 Prototype A：Evidence Object

**目标：**验证合同解析结果能否进入统一 Evidence Object 并回溯原文。

**主要工作：**

- 输入一份合同，输出结构化字段和证据定位。

**Acceptance Criteria：**

- 字段可追溯、结构统一、人工可复核。

### TASK-702 Prototype B：Audit Procedure Orchestrator

**目标：**验证九态状态机、依赖图和局部失败是否正确。

**主要工作：**

- 人为构造 COMPLETED / ABSTAINED / READY / NOT_PERFORMED / NOT_APPLICABLE 等状态组合。

**Acceptance Criteria：**

- 依赖节点正确停用，无依赖节点继续执行，状态原因可解释。

### TASK-703 Prototype C：Partial Input E2E

**目标：**验证只有部分资料时系统仍能完成最大可执行范围。

**主要工作：**

- 仅上传 1 份合同，运行收入审计。

**Acceptance Criteria：**

- 系统不报错。

- 合同相关能力完成。

- 其他程序正确分类为 PARTIAL / BLOCKED / NOT_PERFORMED / NOT_APPLICABLE / ABSTAINED。

- 输出 Execution Manifest 与 Coverage & Limitations。

- 生成当前可生成的底稿。

# 四、MVP 1.0 Definition of Done

- 任意合理资料子集不会导致系统整体崩溃。

- 审计程序能够独立启停。

- 九态 Execution Status 正确运行。

- Procedure Dependency 正确，局部失败不扩散。

- Evidence Object 使用统一 Schema。

- 重要 AI 结论可以回溯原始资料。

- Evidence Chain 可以部分形成。

- 所有正式输出包含 Coverage & Limitations。

- 人工可以确认、修改、拒绝或要求更多证据。

- 人工修改和程序配置均有 Audit Trail。

- NOT_APPLICABLE / NOT_PERFORMED / BLOCKED / ABSTAINED 能正确区分。

- AI 不会把资料未提供自动解释为审计师未执行程序。

- 底稿仅基于 Confirmed Evidence 和实际执行范围生成。

- Replay 能恢复历史输入、版本和原始输出。

- TC-17、TC-18 及核心 Partial Input 测试通过。

# 五、架构基准原则

**核心原则：**Agent 不是架构，Audit Procedure 才是架构。

LLM 只是某些 Audit Capability 内部用于提取、分析和判断的一种工具。真正决定系统能否在真实审计项目中稳定工作的，是 Project Context、Structured Evidence、Rules、Audit Capabilities、Procedure Dependency、Execution State、Human Review 与 Audit Trail。

后续任何新增功能，应优先判断其属于哪个 Stage、调用哪个 Procedure、产生什么 Evidence、依赖什么输入、失败时进入什么状态、如何被人工复核和如何进入底稿，而不是先创建一个新的 Agent。
