# AI for Audit 第一轮整改任务书 V1.0

**项目**：AI for Audit——收入循环智能审计助手  
**阶段定位**：外部评审后的第一轮缺陷整改与可信链路加固  
**版本**：V1.0  
**日期**：2026-09-26  
**适用仓库**：`annawisp/AI-for-audit`  
**外部评审基线**：`main@978c57769c12ef8e8767f73d09e46a48de9604f4`（2026-09-25）

---

## 1. 任务背景

当前项目已经具备项目与文件管理、文档解析、合同字段提取、收入确认分析、收入风险提示、Evidence 版本/状态接口等可运行能力，并已形成规则驱动的收入循环审计助手原型。

2026-09-25 外部企业级评审通过代码阅读、后端测试及 API 端到端试跑，确认当前版本存在两项会直接影响审计结果可靠性的 P0 缺陷：

1. **重复解析污染**：同一合同重复解析后，历史 chunk 会与本次解析结果共同进入合同提取，可能把一项履约义务错误识别为多项。
2. **风险识别伪高风险**：风险模块扫描上游 Evidence 的完整 JSON 文本，字段名、解释文字以及“无需验收”等否定表达也可能触发高风险规则。

同时，外部评审和 TASK-305 验收暴露出一组相关问题：无资料场景仍可能生成有业务含义的风险等级；`NOT_PROVIDED`、`INSUFFICIENT_DATA`、`UNMATCHED` 等状态语义尚未完全分离；匹配链路缺少完整 `match_status`；异常信号与正式审计结论的边界不够明确；跨模块 Evidence 的版本与对象配对约束不足。

因此，本轮不继续扩展知识图谱、大模型判断、复杂 Agent、完整复核工作台等新能力，而是优先解决会导致错误事实、错误风险和不可追溯结果的问题。

---

## 2. 本轮整改目标

本轮目标不是把系统直接改造成企业级完整审计平台，而是把当前原型从“能够跑通规则流程”提升到：

> **同一输入能够稳定重跑；下游只读取明确事实；资料不足时正确停止判断；关键结果可以追溯到指定输入版本；异常信号不会被误当成正式审计结论。**

完成本轮后，系统至少应满足：

- 同一合同重复解析不会改变合同事实集合；
- 风险规则不会因为 JSON 字段名、代码标识或否定语句本身误触发；
- 无有效资料时系统能够弃答，而不是制造风险等级；
- 下游分析能够知道自己使用的是哪一次解析、哪一份 Evidence；
- 系统能够区分资料未提供、资料不足、未匹配、异常线索与人工审计结论。

# 4. TASK-401：重复解析隔离与 Parse Run 版本绑定

## 4.1 问题

当前合同提取按 `project_id + document_id` 读取该文档全部历史 chunk。同一文件解析两次后，旧 chunk 与新 chunk 同时进入合同字段提取，导致重复事实、伪多项履约义务及后续风险误报。

## 4.2 改造目标

一次合同提取必须明确绑定**唯一一次解析运行**，不得默认读取某文档全部历史解析结果。

## 4.3 实现要求

1. 每次解析生成并持久化唯一 `parse_run_id`。
2. chunk 必须可反查所属 `parse_run_id`。
3. 合同提取必须显式指定或受控解析出唯一 `parse_run_id`。
4. 查询 chunk 必须加入 `parse_run_id` 过滤。
5. 同一 `source_span` 在同一 run 内防重复。
6. 建议记录 `document_id / artifact_sha256 / parser_version / parse_run_id / created_at`。
7. 旧数据无法确认解析版本时标记 `legacy_unversioned` 或等价状态。
8. 不得用“解析前删除历史 chunk”掩盖问题，历史运行需保留。

## 4.4 验收

- 同一份仅含一项履约义务的合同连续解析 3 次，每次仍只提取一项义务。
- 同一 document 的多个 parse run 有独立 ID，可分别查询。
- 错误或不存在的 `parse_run_id` 不得静默回退读取全部历史 chunk。

# 5. TASK-402：收入风险引擎结构化事实改造

## 5.1 问题

当前风险能力会把完整 Evidence JSON 序列化成字符串后搜索 `obligation`、`allocation`、`acceptance` 等关键词，导致字段名、解释文字和“无需验收”等否定表达也可能触发风险。

## 5.2 改造目标

风险判断必须读取**明确的结构化业务事实**，不得扫描整个 Evidence JSON、字段名、解释文字或代码标识决定风险等级。

## 5.3 实现要求

1. 禁止完整 Evidence JSON 文本搜索作为风险触发机制。
2. 每条规则明确读取字段、触发条件、排除条件、UNKNOWN/CONFLICTING 处理及来源。
3. 区分明确需要验收、明确无需验收、未提及验收、验收证据冲突。
4. 单一履约义务不得因 schema 存在 `obligation/allocation` 字样而升级风险。
5. 风险输出尽可能包含 `rule_id`、触发事实/来源、`reason`、`is_audit_conclusion=false`。
6. 本轮继续使用规则引擎，不要求接入 LLM。

## 5.4 验收

- 单一义务、无需分摊：不得因字段名触发 HIGH。
- 明确“无需验收”：不得因“验收”字样触发截止高风险。
- 真正多项义务且缺分摊依据：可形成风险线索，但必须说明触发事实。
- “需验收”与“无需验收”并存：进入 `CONFLICTING` 或人工确认，不得任意选边。

---

# 6. TASK-403：缺失资料弃答与状态语义统一

## 6.1 改造目标

让系统区分“没给、给了但不够、有资料但对不上、确实不适用、证据冲突、系统主动弃答”。

## 6.2 实现要求

1. 无有效输入时不得输出 HIGH/MEDIUM/LOW。
2. 无资料场景进入 `ABSTAINED` 或 `NEED_MORE_EVIDENCE`，项目内统一主状态。
3. `NOT_PROVIDED` 与 `INSUFFICIENT_DATA` 必须分开。
4. 有记录但无法配对时使用 `UNMATCHED`。
5. 有相互矛盾有效事实时使用 `CONFLICTING` 或等价状态。
6. `NOT_APPLICABLE` 只用于根据业务事实确认不适用。
7. `execution_status`、数据状态、`judgment_status/review_status` 不混用。
8. TASK-305 已定义相关结构时，以其为基础补齐，不得回退。

## 6.3 状态解释

| 状态 | 含义 | 是否允许形成风险等级 |
|---|---|---|
| `NOT_PROVIDED` | 要求资料未提供 | 否 |
| `INSUFFICIENT_DATA` | 已提供但不足 | 否/仅提示补证 |
| `UNMATCHED` | 两侧记录存在但未匹配 | 可形成异常线索，不等于审计结论 |
| `CONFLICTING` | 有效证据互相冲突 | 不形成确定结论 |
| `NOT_APPLICABLE` | 根据业务事实确认不适用 | 否 |
| `NEED_MORE_EVIDENCE/ABSTAINED` | 程序主动停止判断 | 否 |
| `COMPLETE` | 程序完成其允许执行的分析 | 取决于具体结果 |

# 7. TASK-404：Evidence 输入版本、对象配对与审计结论边界加固

## 7.1 改造目标

在不一次性重建完整 Evidence Graph 的前提下，为关键跨模块调用增加最低限度的对象一致性、版本一致性和结论边界约束。

## 7.2 实现要求

1. 下游 Evidence 至少校验：`project_id` 一致、合同/文档对象一致或有明确关联、解析/输入版本可追溯、Evidence 未明确失效/拒绝。
2. 不允许仅因两个 Evidence 属于同一项目就自动配对。
3. `matched_links` 补充并稳定输出 `match_status`。
4. 记录级匹配尽可能具有 `source_record_id` 和 `target_record_id`；节点级关系必须明确类型。
5. 未匹配记录明确标记 `UNMATCHED`。
6. 自动异常/风险信号统一表达 `is_audit_conclusion=false` 或等价机器字段。
7. 人工复核状态与系统判断状态分离。
8. 本轮不要求完整登录/RBAC，但不得扩大“任意 reviewer 字符串等于正式签字”的业务含义；暂不能整改时须明确 Demo 限制。

## 7.3 验收

- 同项目合同 A 与合同 B 的 Evidence 不得静默串证。
- 风险结果可反查上游 Evidence 与解析版本。
- 未匹配记录明确 `UNMATCHED`，异常对象不宣称审计结论。
- 明确失效/拒绝 Evidence 不得默认作为新分析输入。

---

# 8. TASK-405：P0/P1 反例测试与回归门禁

必须至少覆盖：

1. 同文件连续解析 3 次，合同事实数量不变；
2. 单一履约义务对象含 `performance_obligation_assessment` 等字段名，不因此触发 HIGH；
3. “无需验收”不因出现“验收”字样自动升高风险；
4. 零上游资料必须弃答，不生成 HIGH/MEDIUM/LOW；
5. 同项目不同合同 Evidence 不得静默配对；
6. “需验收”与“无需验收”并存进入冲突/人工复核；
7. `NOT_PROVIDED / INSUFFICIENT_DATA / UNMATCHED` 分别有测试；
8. 系统生成风险/异常明确 `is_audit_conclusion=false` 或等价字段；
9. 原有有效后端测试不得无理由删除或弱化断言。

测试不能只验证 HTTP 状态码，必须验证业务状态和关键字段；每个 P0 必须保留“修复前失败、修复后通过”的反例。

# 9. 推荐实施顺序

1. **TASK-401**：先解决解析输入污染；
2. **TASK-402**：再解决风险读取表达文字而非业务事实；
3. **TASK-403**：统一缺资料、未匹配、冲突和弃答语义；
4. **TASK-404**：加固 Evidence 版本、对象配对和结论边界；
5. **TASK-405**：汇总补齐反例并形成回归门禁。

> 测试应随 TASK-401～404 同步编写；TASK-405 是最终汇总和门禁，不代表前四项可以最后才补测试。

# 10. 本轮总体验收标准（Definition of Done）

### A. P0 缺陷关闭
- 重复解析不造成事实重复；
- 风险模块不再扫描完整 Evidence JSON 决定风险；
- 外部评审两个伪高风险案例通过负控。

### B. 缺资料行为正确
- 零资料主动弃答；
- 不产生 HIGH/MEDIUM/LOW；
- 明确缺什么资料或为何不能继续。

### C. 状态语义正确
- `NOT_PROVIDED / INSUFFICIENT_DATA / UNMATCHED / NOT_APPLICABLE / CONFLICTING` 不混用；
- TASK-305 已形成的状态/匹配设计不得回退。

### D. 最低版本链形成
至少可追溯：

`document/artifact → parse_run → chunk/fact → upstream Evidence → risk/signal`

本轮不要求一次完成最终企业级 `artifact_hash → parse_run → fact → rule → signal → review`，但不得阻碍后续迁移。

### E. 审计责任边界明确
- 自动风险/异常均为待复核线索；
- 系统输出不得伪装成人工确认结论；
- 人工复核状态与系统执行状态分离。

### F. 回归通过
- 原有有效测试继续通过；
- 新增反例测试全部通过；
- 静态检查通过；
- 不得通过删除测试、弱化断言、硬编码样例结果达标。

# 12. 本轮完成后的阶段

第一轮通过后，再启动**第二轮：稳定数据契约与审计程序链**，重点考虑：

- `ProjectContext / SourceArtifact / ParseRun / Fact / ProcedureRun / Evidence/Review` 稳定实体模型；
- 数据质量门真正控制下游执行；
- rule pack / capability manifest / procedure manifest；
- 审计程序状态机；
- 更完整的事实—规则—证据—结论版本链；
- 专业案例集与独立 Oracle。

底层契约稳定后，再评估模型判断、Skill Registry、知识关系/知识图谱、自动编排和复核工作台。

---

## 13. 开发原则

1. **先正确，再智能。**
2. **先事实，再风险。**
3. **资料不足就停。**
4. **所有结果可回溯。**

> 本任务书用于第一轮整改实施与验收。外部企业级评审中的长期架构建议保留为后续路线输入，不在本轮一次性实施。
